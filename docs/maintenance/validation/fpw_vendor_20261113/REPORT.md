# Compiled FPW vendor versus RS physical-plane qualification

## Result

**All 10 comparisons are bit-for-bit identical: 41,295 f32 channel pairs,
zero differing words, maximum absolute error 0, and RMSE 0.** Inputs also match
byte-for-byte. All effective runtime parameters match after excluding the
intentional RS `gpu_multilayer: true` opt-in field, which the FPW vendor does not
have because its color multilayer path is already selected by `sublayers_active`.
Every output is finite and nonuniform; `comparison.json` records output ranges,
distinct values, input/output hashes, and per-case metrics.

This comparison compiles the **actual pinned FPW vendored core/GPU/math/model
sources**. It does not use an older RS revision as a substitute reference.

| Role | Fixed source |
| --- | --- |
| Reference | [FPW `ae3428acd98e39c48784a79dc8f3369ab1236cb1`](https://github.com/ye602a/fursuit-photo-workflow/tree/ae3428acd98e39c48784a79dc8f3369ab1236cb1/native/vendor/spektrafilm), `native/vendor/spektrafilm` |
| Candidate | [RS `c0308a25e5d98f8db9864ceef191e2a9aeee4e43`](https://github.com/ye602a/spektrafilm-rs/tree/c0308a25e5d98f8db9864ceef191e2a9aeee4e43), clean worktree when recorded |

| Rust toolchain | rustc 1.100.0 (`0ef1bc386`, 2026-11-09), cargo 1.100.0 (`3acc79c0c`, 2026-11-05), `x86_64-unknown-linux-gnu` |

## Cases and output boundary

Each route uses a 32×19 local-coordinate fixture and a 65×33 source-coordinate
fixture. These contain deterministic colored ramps, variation and brighter
samples generated by the delivered probes; no private photographs are used.

| Route | Local f32 channels | Source-coordinate f32 channels | Differing words | Maximum error |
| --- | ---: | ---: | ---: | ---: |
| Pro400H → Portra Endura paper | 1,824 | 6,435 | 0 | 0 |
| Provia 100F slide scan | 1,824 | 6,435 | 0 | 0 |
| Velvia 100 slide scan | 1,824 | 6,435 | 0 | 0 |
| Pro400H negative transmission, linear AP0 | 1,824 | 6,435 | 0 | 0 |
| X-Tra 400 negative transmission, linear AP0 | 1,824 | 6,435 | 0 | 0 |

The comparison boundary is the complete GPU-resident physical chain's returned
f32 plane, **before** the separate calibrated output consumer or RGB16
quantization. Paper/slide results use their existing encoded sRGB output.
Negative transmission results use the existing unencoded `ACES2065-1` transport,
with scan glare, transport gamut mapping and transport sharpening off. This AP0
transport is part of the frozen negative route, not new wide-gamut research.

Grain sublayers and grain rendering are enabled on both engines. RS explicitly
opts into its GPU multilayer path. Source-coordinate cases additionally use the
affine map `[0, 1, 2, -1, 0, 96]`, a 128×128 source frame, and the existing output
sampling `[2.0, 0.75]`. Local-coordinate cases leave both options absent.

The FPW probe applies the stock setup statements from pinned
[`film.rs` lines 108–122](https://github.com/ye602a/fursuit-photo-workflow/blob/ae3428acd98e39c48784a79dc8f3369ab1236cb1/native/crates/fpw-runtime/src/film.rs#L108-L122):
usage/antihalation-dependent halation constants and the Provia/Velvia slide DIR
scales. The RS probe selects `AcceptedStockSetup::FpwV1` instead. The remainder
of the recipe and synthetic-input code is identical. Both require a resident
GPU result and `PASSTHROUGH_SHADERS`; neither silently falls back to CPU.

## Reference extraction and resources

`source-blobs.json` identifies **95 verified Git blobs**, comprising the four
numerical crates, referenced shader/SPIR-V sources, original manifests/lock, and
engine metadata/licenses. Eighty-nine files were fetched from the fixed FPW
commit through the GitHub connector. Six existing RS files were reused only
after their complete Git blob hashes matched the FPW tree exactly, including
the grain IIR SPIR-V. Every extracted file was independently rehashed using
Git's `blob <length>\0<bytes>` representation and SHA-256.

The reference build retains **all original numerical Rust, WGSL and SPIR-V
bytes**, including their line endings. Its only workspace-manifest adaptation
removes unused CLI/GUI members. A separate probe package supplies the host/API
adapter and enables system OpenBLAS. No production source was changed to obtain
matching results, and neither FPW nor the candidate RS production tree was
edited by this qualification.

Both binaries read the same 55 engine resource files from the candidate data
directory, permitted by the independent strict resource audit. Seven match FPW
exactly; 48 differ only by LF versus CRLF. `resources-55.json` retains each RS
SHA-256/Git blob and corresponding FPW RESOURCE_PIN SHA-256/Git blob. All 55
actual input files were rechecked against the recorded RS SHA-256 immediately
before this result was packaged. There are no resource-number differences.

## Dependencies were not silently normalized

The pinned vendor's checked-in `Cargo.lock` still contains wgpu 24.0.5, whereas
its checked-in manifest requires wgpu **30.0.1** and newer dependency versions.
The baseline therefore resolves the **original declared requirements** and
records the resulting complete lock in `locks/fpw.Cargo.lock`. No dependency
requirement was downgraded or replaced to match RS.

The candidate probe is seeded from the candidate RS lock and retains those
versions, with the probe package/system-OpenBLAS feature dependency added.
Its complete resolution is `locks/rs.Cargo.lock`. The observed important
differences are explicit:

| Dependency | FPW reference build | RS candidate build |
| --- | --- | --- |
| wgpu / core / hal / naga | 30.0.1 / 30.0.2 / 30.0.2 / 30.0.2 | Same |
| serde / serde_json | 1.0.229 / 1.0.154 | 1.0.228 / 1.0.149 |
| rand / rand_distr / rand_mt | 0.10.3 / 0.6.0 / 6.1.0 | 0.9.4 / 0.5.1 / 5.0.0 |
| pollster | 1.0.1 | 0.4.0 |
| cblas | 0.4.0 and 0.5.0 | 0.4.0 |
| blas-src | 0.10.0 and 0.14.0 | 0.10.0 |
| openblas-src / libm / rayon | 0.10.16 / 0.2.16 / 1.12.0 | Same |

Both binaries link the same system OpenBLAS library. Full version metadata is in
`dependency-resolution.json` and `run-metadata.json`. This is a freshly compiled
reference from the pinned engine source, not a claim about the exact dependency
closure or binary of an originally packaged FPW Windows application.

## Reproduction

Obtain authorized checkouts of the two fixed commits above. The preparation
script reads only the listed engine files and audited resource files; it does
not inspect other FPW application data. It performs no network or credential
operations. Choose a fresh scratch directory:

```sh
python prepare.py \
  --fpw-vendor /path/to/fpw/native/vendor/spektrafilm \
  --rs-root /path/to/spektrafilm-rs \
  --work-dir /tmp/fpw-physical-qualification
```

This verifies the 95 reference blobs, candidate source hashes and 55 resources,
then creates separate reference/candidate probes. `probes/fpw.rs` and
`probes/rs.rs` are the actual sources used for this result. Their Cargo manifests
retain the actual package/dependency declarations, with only the engine root
replaced by `${ENGINE_ROOT}` for portability. The script restores real paths
and installs the delivered resolved locks.

Use the recorded Rust toolchain, an available system OpenBLAS and Vulkan driver.
The original run selected Mesa's `lvp_icd.json` using `VK_DRIVER_FILES`, supplied
its OpenBLAS library directories through `LIBRARY_PATH`/`LD_LIBRARY_PATH`, and
used the following build/run sequence:

```sh
export OPENBLAS_NUM_THREADS=1
export CARGO_TARGET_DIR=/tmp/fpw-physical-qualification/target

cargo build --locked \
  --manifest-path /tmp/fpw-physical-qualification/probe-fpw/Cargo.toml
cargo build --locked --features candidate \
  --manifest-path /tmp/fpw-physical-qualification/probe-rs/Cargo.toml

"$CARGO_TARGET_DIR/debug/qualification-probe-fpw" \
  /tmp/fpw-physical-qualification/data \
  /tmp/fpw-physical-qualification/outputs-fpw
"$CARGO_TARGET_DIR/debug/qualification-probe-rs" \
  /tmp/fpw-physical-qualification/data \
  /tmp/fpw-physical-qualification/outputs-rs

python compare.py \
  /tmp/fpw-physical-qualification/outputs-fpw \
  /tmp/fpw-physical-qualification/outputs-rs \
  --output /tmp/fpw-physical-qualification/comparison.json
```

`compare.py` requires only Python's standard library. It checks equal input
bytes, finite/nonuniform output, exact f32 words and effective parameters, and
exits nonzero if the numerical or parameter comparisons differ.

## Scope and limitations

This provides an independent, actual-FPW numerical baseline for five accepted
routes and two source/sampling configurations on one software Vulkan runtime.
It does not qualify six frozen photographs, RTX/Intel/AMD hardware, a Windows
surface, full-size export, every lens/diffusion/DIR parameter, wide-blur IIR
extremes, cancellation, or FPW's scheduling/undo behavior. Those remain covered
by their own focused tests or later product integration gates. No FPW dependency
pin was switched by this result.

The calibrated negative inversion/output consumer is deliberately outside this
comparison boundary and has its separate original-FPW shader/scalar comparison.
The seconds present in the case metadata are diagnostic timings only: shader
compilation and driver-cache warmness differed between launches. They must not
be presented as a performance comparison.

The evidence set contains metadata, two synthetic probes, build manifests and
locks, and preparation/comparison scripts. It excludes compiled binaries,
duplicate vendor source trees, dependency caches and photographs.
